not establish support for other boards, recovery after interrupted writes, or
downgrades.

## Observed update

The user authorized the physical update, maintenance shutdown and reboot, and
subsequently authorized the two LXC shutdowns. Running workloads and service
configuration were saved before maintenance. Both CI runners had no running
job containers. Docker containers, virtual machines and LXC containers were
shut down; Docker and VM Manager were disabled. No forced workload kill was
needed. Management used Unraid's direct HTTPS endpoint, independent of Docker's
reverse proxy.

The fresh compatibility check passed the PCI/MEI identity, image hash, newer
same-project version, Intel compatibility, idle GPU and online UPS checks.
The exact-card confirmation form was submitted once. The persistent journal
records the start at `2026-11-24T15:45:41+00:00`.

One native `igsc fw update --device ... --image ...` process was observed. The
tool reached 100%; the plugin's transcript/diagnostic checks passed, and its
separate version read returned `DG02_2.2359`. The journal transitioned to
`reboot_required`. The process had exited before a normal Unraid reboot was
requested. No force, downgrade or second flash invocation was used. OPROM,
board firmware data and HDMI firmware were not written.

## Post-reboot verification and restoration

The plugin's **Verify after reboot** action completed at
`2026-11-24T15:59:44+00:00`. The boot ID changed; the exact PCI identity matched;
the Intel interface returned `DG02_2.2359`. The durable journal is `complete`.
The single flash worker completed in 54 seconds, including its preflight and
read-back checks.

The running-name lists matched before and after maintenance: 59 Docker
containers, six VMs and two LXC containers. The original Docker and VM Manager
configuration files were restored and compared by SHA-256. No Docker container
reported unhealthy in the final check. This verifies running state, not every
application's business functionality.

The i915 boot log shows normal driver initialization and authenticated HuC.
It also reports a 256 MiB BAR because the platform lacks Resizable BAR support;
that observation is not a firmware-update failure. No GPU hang was observed.

Plex's own transcoder completed a bounded **48-frame H.264 VAAPI encode** as
UID 99/GID 100, using its existing iHD driver and the render node mapped to the
A380. Exit status was zero. Input was synthetic 640×360 NV12 data from
`/dev/zero`; output went to the null muxer. No user media was read or changed.
Two setup attempts exposed Plex-specific CLI requirements: the driver cache
path must be supplied to an independently invoked transcoder, and its build
does not include the `lavfi` input demuxer. These were test-harness issues,
not additional firmware writes. A Plex-client playback session, decoding,
HDR tone mapping, other codecs and long-duration stability were not tested.
